# ADR-0002 停诊两段式（登记 → 处理）与批号幂等

- 状态：已采纳
- 影响面：分诊台停诊上报、管理端停诊处理、号源回池、通知与退款

## 背景

停诊不是一个瞬时动作：分诊台知道「某医生某半天不能出诊」，但真正取消号源、通知患者、产生退款，
需要管理端确认范围（按排班 / 按医生某日 / 按院区某日）后再执行。若做成一步，最直接的问题是
**误操作无法挽回**——一旦处理就把当天号源全撤了。

批量操作还带来第二个问题：网络重试、手抖连点会重复提交同一批登记，导致重复回池与重复通知。

## 决策

1. **两段式**：`登记（PENDING）` 与 `处理（HANDLED）` 分离。登记只落「范围 + 原因 + 生效区间」，
   不改号源；处理时才按范围展开、回池、发通知、触发退款。
2. **批号幂等**：批量提交带批号（batch id），服务端以批号为幂等键；同一批号重复提交只生效一次，
   已处理的登记不允许再次处理。
3. **范围用复合键表达**（见 ADR-0004）：`scope_type` + `scope_value` 决定展开口径，
   展开逻辑集中在 Service，页面只传范围，不各自拼 SQL。

## 后果

- 好处：可回滚窗口（登记后处理前可撤销）、批量重试安全、责任边界清晰（分诊登记 / 管理处理）。
- 代价：状态机多一个中间态，列表页要区分「待处理 / 已处理」，后台首页的「待处理停诊」才有意义；
  处理是长事务，需要按范围分页回池，避免一次锁太多行。
- 副作用：处理会写站内信与号源台账，测试时不能用「登记条数」直接推断「影响号源数」。
