# ADR-0004 停诊范围用 `scope_type + scope_value` 复合键

- 状态：已采纳（含两次缺陷修复）
- 影响面：停诊登记与处理、号源回池范围、分诊台与后台的入参校验

## 背景

停诊要表达三种范围：按排班、按医生某日、按院区某日。早期实现有两个坑：

1. **只按 `scope_value` 判断**：`scope_value` 存的是 id 字符串，不同 `scope_type` 下同一个数值含义完全不同
   （院区 id 与医生 id 都是雪花号），仅比对 `scope_value` 会把「按院区停诊」错展成「该 id 的医生」或反之；
2. **页面自拼 `scope_type`**：不同页面（分诊台上报、后台登记）对同一意图传了不同 `scope_type`，
   于是「同一批登记」在处理时展开范围不一致——表现为偶发漏停/多停。

## 决策

- 范围一律用 **`scope_type + scope_value` 复合键**表达，Service 内集中构造，页面只传业务意图；
- `scope_type` 取值收敛为 `SCHEDULE` / `STAFF_DATE` / `CAMPUS_DATE`（契约 §7.5 与 DDL 注释对齐），
  新增类型必须先改契约与字典；
- 范围展开逻辑只有一处（`SuspendScopeResolver` 等价实现），任何页面不得自行拼装查询条件；
- 校验前置：登记时即校验「该范围存在且未处理」，避免处理阶段才发现范围为空。

## 后果

- 好处：三种范围语义互不串号；新增页面复用同一构造器，不会再出现「各拼一套」；
- 代价：入参多一个字段，前端表单必须先选类型再选对象；跨类型批量操作需要后端展开而非前端拼接；
- 回归要点：每次改停诊范围，必须跑三种 `scope_type` 的脚本（见证据），只跑一种会漏掉这类缺陷。
