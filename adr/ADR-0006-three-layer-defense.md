# ADR-0006 余量并发三层防线（Redis 预扣 → DB 单柱 CAS → 应用重试）

- 状态：已采纳
- 影响面：挂号写入路径（B1）、余量查询（A5/A6）、压测结论与故障降级

## 背景

门诊放号是典型的「读多写少但写极度集中」：放号瞬间大量请求命中同一个 `staff + date` 的余量。
只靠数据库行锁在本地压测能过，但一旦 Redis 抖动、或有人把锁去掉，就会超卖。

需要明确「哪一层是权威、哪一层是加速」——否则出问题时会互相甩锅。

## 决策

三层，**职责不重叠**：

1. **Redis 预扣（加速 + 削峰）**：请求先原子扣减 Redis 余量；扣不到直接失败，不打数据库。
2. **DB 单柱 CAS（权威）**：真正的判定在数据库——按「有效挂号数 < 号源容量」做条件更新
   （单柱 CAS），失败即回滚 Redis 预扣。**Redis 挂掉只影响吞吐，不影响正确性**。
3. **应用重试（体验）**：CAS 失败时按短退避重试有限次数，仍失败返回「余量不足」业务码，
   不把数据库异常直接透给用户。

配套：余量缓存读路径（A5/A6）允许短暂不一致，但**不允许超过 1 个 TTL**；
`GET` 语义的查询不做预扣，只有写路径才扣。

## 后果

- 好处：正确性单点可证（DB CAS）；Redis 故障时降级为「慢但不超卖」；
  压测能把「有防线 / 无防线」的差异量化（见证据）。
- 代价：写路径两次状态（Redis + DB）需要补偿逻辑；压测必须同时覆盖「Redis 正常 / 摘除」两种工况；
  缓存 TTL 与预扣的关系要在配置里说清（`BookingProperties` 三个开关）。
