# ADR-0001 限购口径：同一就诊人同一就诊日 1 单

- 状态：已采纳（2026-10-23 起生效）
- 影响面：`appt` 挂号写入路径、患者端「我的预约」、后台对账与风控、演示脚本

## 背景

早期口径按「同一医生 + 同一就诊日最多 1 单，且同一就诊人当日在全院最多 3 单（`HOLD_MAX = 3`）」实现。
实测暴露两个问题：

1. **额度可被绕开**：患者在不同院区/不同医生之间切换，仍能在同一天堆出多张单，
   对「一人一天只能看一次病」的真实业务语义是错的；
2. **口径难解释**：3 这个数字没有业务出处，演示时解释成本高，后台告警阈值也不好定。

## 决策

统一为 **同一就诊人 + 同一就诊日 → 仅允许 1 张有效单**（跨院区、跨医生、跨门诊类型共享同一额度）。

- 判定只认「有效单」（`active_flag = 1`），退号/关闭后额度立即释放；
- 旧的 `HOLD_MAX = 3` 保留常量但标记 `@deprecated`，避免其它分支继续引用；
- 前端不做本地判断，一律由后端拒绝并返回业务码，页面按 `bizMessage()` 展示。

## 后果

- 好处：语义唯一、可解释；退号即释放，用户体验连续；对账口径收敛（一人一日一行）。
- 代价：演示脚本不能靠「反复下单」造数据，必须走「下单 → 支付 → 退号」闭环释放额度
  （`showcase/tools/screenshots` 的 flows 按此设计，见该仓 AGENTS §4）。
- 迁移：存量同日多单不回溯清理，只对新增写入生效。

## 证据

- 常量与注释：`backend/ruoyi-modules/appt/src/main/java/org/dromara/appt/common/ApptConst.java`（限购段，`HOLD_MAX` 已标注废弃与生效日期）
- 回归实测：`docs/test-evidence.md` §14.3（限购口径变更后的回归补齐）
- 脚本实践：`showcase/tools/screenshots`（造数策略受此约束）
